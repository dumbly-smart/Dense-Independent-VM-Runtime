# Controlled two-VM comparison (zero guest RAM divergence)

Run on 2026-10-26 with QEMU 11.1.2, Linux 7.2.11, KVM, 4 KiB pages:

```sh
densevm probe --out RUN_DIRECTORY --count 2 --divergence-percent 0
densevm stats RUN_DIRECTORY/result.json
```

`result.json` is the raw probe output. `summary.json` is generated by the
project's `densevm stats` command. The probe uses the same generated guest
artifacts for the ordinary QEMU baseline and the restored template clones.
Each guest has 256 MiB configured RAM.

## Observed process metrics

| Measurement | Two ordinary VMs | Two template clones, before divergence |
| --- | ---: | ---: |
| Process PSS | 416,436 KiB | 246,887 KiB |
| Process RSS | 453,864 KiB | 307,464 KiB |
| Configured guest RAM | 524,288 KiB | 524,288 KiB |

Clone process PSS was about 40.7% lower for this one run. This is a process
measurement, not a total-host-memory result. QEMU process PSS excludes KVM
metadata and host page tables. The complete 256 MiB template RAM file was
resident in the page cache; the stats command's deliberately conservative
PSS-plus-full-cache figure is 509,031 KiB and double-counts some mapped pages.
The run therefore does not establish a 40.7% reduction in total physical RAM.

The baseline reached READY in 3,057 ms. This experiment does not report a
comparable clone-ready latency. The recorded disk allocation is after the
probe's disk-isolation workload, so it is not an initial-overlay size
measurement. See the raw JSON for identity checks, isolation results, memory
mapping details, and limitations.

This is a single host-specific sample, not a benchmark distribution. Re-run
the command with a fresh output directory to reproduce it; keep the result
directory and host configuration with each run.
