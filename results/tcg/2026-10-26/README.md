# Repeated TCG and KVM baseline

These are two real-QEMU samples per configuration of the conventional baseline.
Each `baseline.json` preserves the exact QEMU commands, host metadata, PSS/RSS,
startup-to-ready time, idle ticks, and active CPU samples. The `baseline-*`
directories contain the first samples; `tcg1b`, `tcg2b`, and `kvm2b` contain
the repeats.

| Accelerator | VM count | Ready time, mean (range) | Aggregate process PSS, mean (range) | Active CPU per process, range |
| --- | ---: | ---: | ---: | ---: |
| TCG | 1 | 8,408 ms (7,728–9,087) | 284,412 KiB (283,390–285,434) | 99–103% of one host core |
| TCG | 2 | 14,509 ms (13,543–15,475) | 553,016 KiB (551,543–554,488) | 102–104% of one host core |
| KVM | 2 | 2,229 ms (2,176–2,281) | 419,144 KiB (416,820–421,467) | 99–104% of one host core |

These two samples per configuration show TCG two-VM readiness taking about
6.5 times as long as KVM two-VM readiness on average. This is a directional
observation, not a statistical result: `n=2`, the runs were sequential rather
than randomized, and TCG uses QEMU's `max` CPU model while KVM uses `host`.
Both active workloads consumed about one host core per QEMU process, consistent
with separate guests still executing their own work.

The untraced runs establish that the local QEMU 11.1.2 TCG path boots this
project guest and provide a basic process baseline. They do not count
translation-block events. Generated-code size and time spent translating
remain unmeasured. The KVM PSS values are QEMU process totals and do not
include KVM or host page-table memory.

Two opt-in one-VM trace runs are saved in [`trace1/`](trace1/) and
[`trace1b/`](trace1b/). They recorded 108,834 and 109,377 `translate_block`
events through the active-workload sample in 8,759,535-byte and 8,803,502-byte
logs. Ready time was 8,063 ms and 7,548 ms; process PSS was 288,175 KiB and
287,784 KiB. The trace is instrumentation, so these timing and memory values
are not directly comparable to the untraced runs. Event count is not a count
of unique TBs and does not measure translation duration or generated-code
size. The traces contained 92,654–92,677 distinct guest PC values; 28,410–
28,999 events fell at 12,230–12,299 PCs observed multiple times. A PC can map
to multiple TBs under different translation state, so these are PC reuse
counts, not unique TB or retranslation counts.

QEMU's `-d out_asm` output includes emitted host-code block sizes, but a manual
probe generated a 395 MB log and did not yield a guest-ready checkpoint within
the observation window. It is not treated as a result. See
[`tcg-sharing-feasibility.md`](../../../docs/tcg-sharing-feasibility.md) for
the limits and next measurement gate.

## Patched QEMU code-size trace

[`codegen3/`](codegen3/) contains a one-VM run using QEMU 11.1.2 built with
[`0001-trace-tcg-generated-block-size.patch`](../../../patches/qemu/0001-trace-tcg-generated-block-size.patch).
It reached readiness in 10,623 ms and recorded 109,238 translation starts,
109,218 completed generated blocks, and 34,171,065 cumulative generated
host-code bytes. The 20-event start/completion count difference is not a
per-block pairing result. The raw trace log is 17,577,176 bytes. DenseVM stops
the traced guest after the active CPU sample, then reads the stable log; an
independent recount matched the JSON values exactly.

The emitted-byte sum is cumulative and may include blocks later discarded;
it is not TCG code-cache residency. The `codegen3` trace does not contain
duration instrumentation. Three subsequent runs using both patches are saved
under [`duration1/`](duration1/), [`duration2/`](duration2/), and
[`duration3/`](duration3/). They measured 108,907–109,285 completed blocks;
34,092,023–34,162,552 cumulative generated bytes; and 1,155,076–1,173,435
microseconds cumulative elapsed wall time around `setjmp_gen_code` (10.57–10.77
microseconds mean per completed block; maximum event durations 530–1,896
microseconds). This is not thread CPU time and may include host scheduling delay. Only successful code-generation calls have a
duration; failed or restarted attempts are excluded, with the separate
start/completion event-count difference retained. These three sequential
samples are directional, not a statistical benchmark. Tracing perturbs timing and
PSS. The patches are not included in the system QEMU binary. `stockduration/`
shows the stock-QEMU fallback: baseline tracing works, and generated-code size
and duration are recorded as unavailable. Build and run instructions are in
[`patches/qemu/README.md`](../../../patches/qemu/README.md).

## Translation activity by workload phase

[`phases1/`](../2026-10-27/phases1/), [`phases2/`](../2026-10-27/phases2/),
and [`phases3/`](../2026-10-27/phases3/) are three patched-QEMU samples with
the trace split at QMP-frozen offsets after `READY`, before the active CPU
workload, and after that workload. Each directory contains its machine-readable
`baseline.json` and raw trace.

| Phase | Translation starts | Completed blocks | Cumulative code bytes | Cumulative wall duration |
| --- | ---: | ---: | ---: | ---: |
| Boot through readiness freeze | 107,795–108,304 | 107,775–108,284 | 33,724,574–33,900,046 | 1,225,067–1,343,860 µs |
| Post-ready idle through pre-active freeze | 189–517 | 189–517 | 65,660–153,949 | 3,824–5,863 µs |
| Active workload through final freeze | 711–763 | 711–763 | 226,886–244,054 | 8,920–18,365 µs |

In all three runs, independent phase recounts match the complete trace, and
phase sums for generated blocks, bytes, and duration equal each run's
full-trace totals. The three sequential runs are directional, not a statistical
benchmark. Each intermediate boundary briefly pauses/resumes the traced VM, so
they are approximate phase boundaries and affect guest timing. Readiness
ranged from 8,145 to 8,797 ms and process PSS from 302,500 to 303,915 KiB;
neither should be compared directly to an untraced baseline.

Three additional one-VM runs used the same patched QEMU binary with tracing
disabled, saved under `results/tcg/2026-10-27/untraced1/` through `untraced3/`.
Their readiness time averaged 8,761 ms (8,331–9,036) and process PSS averaged
299,099 KiB (296,296–301,462), compared with 8,518 ms (8,145–8,797) and
302,994 KiB (302,500–303,915) for the traced phase samples. Readiness time is
measured before the phase-boundary pauses. The PSS ranges overlap, and the
three sequential samples are too few to establish a trace overhead or a
startup benefit; PSS is about 1.3% higher on average with tracing. It includes
the patched binary, trace event output, and post-ready sampling, and is not a
controlled estimate of any one component's cost.

[`stockphase1/`](../2026-10-27/stockphase1/) verifies the same phase split
using the unpatched system QEMU 11.1.2 binary. It recorded 107,551 boot/readiness,
188 idle, and 883 active-workload translation events (108,622 total). An
independent recount matched every raw-log range. As expected, generated block
size and duration are unavailable in stock QEMU, while ordinary phase event
counts remain available.

Reproduce with the patched QEMU binary first in `PATH`:

```sh
PATH=/path/to/qemu-build:$PATH cargo run -- benchmark baseline \
  --count 1 --accel tcg --trace-translations --out /path/to/phases1
```

Reproduce with:

```sh
cargo run -- benchmark baseline --count 1 --accel tcg --out /path/to/tcg-1
cargo run -- benchmark baseline --count 2 --accel tcg --out /path/to/tcg-2
cargo run -- benchmark baseline --count 2 --accel kvm --out /path/to/kvm-2
```

Repeat samples were collected with the same commands and distinct output paths:

```sh
cargo run -- benchmark baseline --count 1 --accel tcg --out /path/to/tcg-1b
cargo run -- benchmark baseline --count 2 --accel tcg --out /path/to/tcg-2b
cargo run -- benchmark baseline --count 2 --accel kvm --out /path/to/kvm-2b
```
